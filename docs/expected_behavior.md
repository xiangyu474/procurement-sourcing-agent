# 系统预期行为说明

这份文档写「系统会发生什么」，不写「代码怎么实现」。面向项目交付后的接手方：产品、测试、运维、采购业务同事。

每一条行为都能在代码或验收脚本里找到出处。想核实的人可以按文末的清单自己跑一遍。

## 一、系统边界

**会做的**

| 行为 | 在哪一步 |
|---|---|
| 从 PPTX / 文本里抽取采购行、技术约束、冲突、非结构化需求 | M1 |
| 导入历史采购 Excel（可选，没有也能继续） | M1 |
| 公开寻源：找到真实企业和具体型号，带可回溯的网页快照 | M2 |
| 把需求约束和型号声明对齐，给出 PASS / FAIL / UNKNOWN | M3-A |
| 复用到别的项目、下次再跑时跳过重复劳动 | M2 |

**不会做的（这些是刻意的）**

| 不做 | 为什么 |
|---|---|
| 不说「技术合格」「已准入」「采购中选」 | M2 的产物是公开线索，不是采购结论 |
| 不把网页挂牌价当正式报价 | 价格口径不同就不能比 |
| 不把 UNKNOWN 改写成 PASS | 证据不足时保守是唯一安全的做法 |
| 不把推断出来的阈值当用户硬性要求 | 推断只能是偏好，要人来确认 |
| 不把历史模拟供应商和现实企业关联 | 模拟数据不能污染公网情报 |
| 不自动合并同名企业 | 同名不等于同一法律主体 |
| 不生成最终报告 / 网页界面 | 属于 M4 |

## 二、一次任务的完整生命周期

```
上传 PPTX/文本
   └─ M1 编译（模型主导）
        ├─ 产出：采购行 + 约束 + 冲突 + 非结构化需求
        ├─ 数字与引文复核：数值必须在引文里，引文必须在源文件里
        └─ 状态：COMPLETED / PARTIAL / FAILED + 原因码
   └─ M2 寻源（Supervisor + Researcher）
        ├─ 产出：供应商、型号、声明、证据快照、候选长名单
        ├─ 候选只停在 DISCOVERED_LONG_LIST
        └─ 状态：COMPLETED / PARTIAL / FAILED + 原因码
   └─ M3-A 技术核验（需求 × 型号）
        ├─ 产出：逐条 PASS/FAIL/UNKNOWN、计算过程、证据引用
        └─ 状态：见第三节
   └─ M3-B 历史与价格 → M3-C 决策与闸门（未开始）
```

**M1 完成后**，可以只跑 M2，也可以直接跑 M3-A。M3-A 不依赖历史数据。

## 三、状态词表

### 运行状态（每一次运行都有）

| 状态 | 含义 |
|---|---|
| `COMPLETED` | 这一阶段该做的都做完了 |
| `PARTIAL` | 做了一部分，剩下的是记录在案的缺口 |
| `FAILED` | 这一阶段没能完成 |

`PARTIAL` 和 `FAILED` **一定带一个原因码**，不存在「失败但不知道为什么」。常见原因码：

| 原因码 | 什么时候出现 |
|---|---|
| `SEARCH_PROVIDER_TIMEOUT` | 搜索服务超时 |
| `SEARCH_PROVIDER_RATE_LIMITED` | 搜索服务限流 |
| `MODEL_TIMEOUT` / `MODEL_RATE_LIMIT` | 模型端点超时 / 限流 |
| `BUDGET_EXHAUSTED` | 单轮搜索或抓取次数用完 |
| `RESEARCH_INPUT_REJECTED` | 研究器要抓的网址越界（私有信息），被拒绝并记录 |
| `RESEARCHER_FINDINGS_INCOMPLETE` | 某个研究任务没有交出结构化结果 |
| `SOURCE_FETCH_FAILED` | 页面读不出内容 |
| `NO_FETCHED_EVIDENCE` | 没有可读来源 |

### 需求状态（每条约束都有）

| 状态 | 含义 | 会不会自动判定 PASS/FAIL |
|---|---|---|
| `RESOLVED` | 解析清楚了，来源和原文都在 | 会 |
| `AMBIGUOUS` | 有歧义，或者数字复核没通过 | **不会**（结论是 UNKNOWN） |
| `UNSUPPORTED` | 无法安全变成可比较的条件 | 不会 |

### 技术判定（每条约束 × 一个型号）

| 判定 | 含义 |
|---|---|
| `PASS` | 需求被证实满足，且证据可回溯 |
| `FAIL` | 需求被证实不满足 |
| `UNKNOWN` | 判断不了 |

**UNKNOWN 不是失败，也不是通过。** 它表示「现在手上的证据不足以判断」，每个 UNKNOWN 都带原因码：

| 原因码 | 含义 |
|---|---|
| `MISSING_CLAIM` | 这个型号没有对应的声明 |
| `UNVERIFIED_CLAIM` | 声明的数字在它自己的引文里找不到 |
| `INCOMPLETE_SOURCE` | 声明读不出单一值 |
| `AMBIGUOUS_REQUIREMENT` | 需求本身有歧义 |
| `ATTRIBUTE_NOT_ALIGNED` | 两边量的不是同一个东西 |
| `UNIT_NOT_CONVERTIBLE` | 单位不在白名单内，或量纲不同 |
| `CONDITIONAL_MISMATCH` | 限定条件对不上（模式、变体） |
| `CONFLICTING_CLAIMS` | 不同来源给了互相矛盾的值 |
| `MODEL_VARIANT_UNCERTAIN` | 候选没有精确型号码 |
| `UNVERIFIED_CLAIM` | 声明没有来源支持 |
| `NO_HARD_CONSTRAINT` | 这条需求没有硬约束 |
| `UNRESOLVED_DEMAND` | 还有没能编译成约束的硬性需求 |
| `VERIFIED_COMPARISON` | 唯一能给 PASS / FAIL 的原因码 |

### 整体结论（一条需求 × 一个型号）

| 结论 | 什么时候出现 |
|---|---|
| `FAIL` | 有一条硬约束被可靠地证伪（其余 UNKNOWN 也照样 FAIL） |
| `PASS` | 所有硬约束都 PASS，且没有未决需求 |
| `UNKNOWN` | 其余全部情况，**包括一条硬约束都没有** |

### 对齐状态（约束 ↔ 声明）

| 状态 | 含义 |
|---|---|
| `ALIGNED` | 两边量的是同一个量，可以比 |
| `NOT_ALIGNED` | 不是同一个量 |
| `AMBIGUOUS` | 说不准，需要更多信息 |
| `CONFLICTING` | 来源之间互相矛盾 |

### 候选阶段

| 阶段 | 含义 |
|---|---|
| `DISCOVERED_LONG_LIST` | 公开线索，还在长名单上 |
| `SCREENED` / `NEEDS_VERIFICATION` / `RFQ_SHORTLIST` / `EXCLUDED` | M3 之后的阶段，M2 不会产出 |

## 四、关键预期行为

### 1. 需求的条数、数量、金额由模型给出

M1 是模型主导的抽取：**需求有几条、每条多少钱，代码不保证**，出处是模型。代价是已知的，换来的是「不写死表头解析器」。需求文本里客观的规格（5MP、IP66、−20~80℃）会被抽成带引文的约束，不能只留在品名里。

**怎么查**：看编译结果的 `source_ref` 和 `source_quote`，两者都能指回原文。

### 2. 数字和引文会被程序复核

每条约束的引文必须出现在被引的原文片段里，数值必须出现在引文里（支持「500万像素」这类量纲换算）。复核不过的约束被标成 `AMBIGUOUS`，**不会被自动判 PASS/FAIL**。数量、单价、预算**一个字节都不改**，只记录 issue 和待确认问题。

项目合计会被重算并分类：算术错误 / 逐行取整造成的舍入误差 / 源表本身不一致，三者分得开。

### 3. 硬约束 FAIL 不会被叙事推翻

计算器给出 FAIL 之后，任何叙述都不能把它变回 PASS。除非有**新证据**并且**重算了**。

### 4. UNKNOWN 永远保持 UNKNOWN

对齐不上、单位换不了、声明没来源——任何一种情况都是 UNKNOWN，并且说明缺什么。**系统不会用「同品类」「同系列」来补齐。**

### 5. 没有硬约束就不给 PASS

一条需求如果没有硬约束，整体结论是 UNKNOWN，不会说「技术符合」。有没能编译成约束的硬性需求时也一样。

### 6. 技术核验的最小单位是「需求 × 型号」

同一企业的不同型号**分别评价**，不合并成供应商级结论。候选行可能指向同一个型号，那时结论共享，但不会产生两个互相矛盾的结论。

### 7. 证据必须能复核

- 只有**抓取到的页面正文**能支持一条声明，搜索摘要不算证据。
- 每条声明的引文必须在 R2 快照正文里逐字找得到。
- R2 快照的 SHA-256 必须和 D1 里的元数据一致。
- 型号级结论必须有型号级证据；没有精确型号码的候选只能得到 UNKNOWN。

### 8. 价格口径不同就不比

（属于 M3-B，已定口径）预算、历史成交价、公开参考价、正式报价是四种不同的东西。口径不足时标记为不可直接比较，**不计算虚构的节支率，也不给最低价**。

### 9. 价格按口径比，口径不同不比

（M3-B 已定口径）预算、历史成交价、公开参考价、正式报价是四种不同的数字：

| 比较 | 结果 |
|---|---|
| 同类的两个价格 | 可比，给最低价 |
| 正式报价 vs 预算 | 可比，给节支额和节支率 |
| 正式报价 vs 历史成交价 | 可比（本次报价 vs 历史） |
| 历史成交价 vs 预算 | 可比（预算 vs 历史） |
| **公开参考价 vs 任何其他** | **不可比**——挂牌价不是报价，不产生节支 |

另外，币种、含税口径、单位（每套 / 每台）任一不一致都判不可比。单位或含税口径缺失时同样判不可比。

**混在一起的一堆价格不给最低价。** 如果一个集合里混了不同口径的价格，最便宜的那个不是买家能据以行动的数字，所以整套判为不可比，只列出被排除的观察值。

### 10. 历史与公网按确认的等价关系融合

融合的键是**确认过的产品等价关系**，绝不是供应商名称。同名供应商但没有确认过等价的两条记录不会被合并。未经确认的关系不进索引。

### 11. 决策要过闸门才算数

（M3-C）模型只写「建议」，闸门核对「结论」。以下情况决策**不被采纳**，并记录被拦下的原因：

| 情况 | 结果 |
|---|---|
| 硬约束 FAIL 的型号进了短名单 | 拒绝，留下失败原因 |
| 技术结论是 UNKNOWN，却写成「已核实通过」 | 拒绝 |
| 技术结论与实际计算结果矛盾 | 拒绝 |
| 引用了不存在的证据 ID | 拒绝（真实存在的证据仍保留） |
| 写了分析里没有的节支额 | 拒绝 |
| 写了节支额却没给出价来源 | 拒绝 |
| 没有评估就下结论 | 拒绝 |
| UNKNOWN 的型号进短名单但没写缺什么 | 拒绝 |

UNKNOWN 的型号**可以**进短名单，前提是决策写清了缺什么——短名单是去问供应商，不是宣布合格。

被拒的决策**照样存下来**，连同被拒的原因，不是不留痕迹地消失。

### 12. 模拟历史与公网隔离

历史 Excel 里的模拟供应商有自己的命名空间，**永远不会被自动映射到现实企业**。按供应商名 JOIN 历史和公网数据是被禁止的，只能按需求/SKU 和确认的产品等价关系融合。

## 五、失败时会发生什么

**模型 provider 故障（5xx / 超时）在 M3 的三步里都不会让整次流程崩掉**：类型化的那一批声明保持未类型化、对齐保持未对齐、决策保持空缺，结论都是 UNKNOWN，而不是报错退出。

| 情况 | 系统行为 |
|---|---|
| 搜索服务超时 / 限流 | 这一轮记 `PARTIAL` + 原因码，已抓到的证据保留 |
| 单轮搜索或抓取用完预算 | 研究器带着已抓到的来源继续作答，缺口记进 `unresolved_gaps` |
| 研究器要抓越界网址 | 拒绝，记录一条 `RESEARCH_INPUT_REJECTED` 动作，**不落库网址** |
| 页面读不出内容 | 记 `SOURCE_FETCH_FAILED` 继续 |
| 研究器答成散文 | 系统带着已抓的来源再问一次，这次强制要求结构化工具调用 |
| 编译返回空的采购行 | 重新问，最多三次；三次都空才接受空结果并记录 |
| 模型 provider 故障（5xx / 超时） | 类型化和对齐各自重试一次；仍失败则相关声明保持未类型化、结论保持 UNKNOWN，**整次评估不会崩** |
| 容器内部未捕获异常 | 返回错误类型和脱敏后的消息，存进运行记录 |
| 幂等请求 | 同一个幂等键返回同一个结果，不产生重复数据 |

## 六、数据落在哪里

| 层 | 存什么 | 不存什么 |
|---|---|---|
| **D1** | 结构化事实：项目、需求、计划、任务、情报、声明、证据、候选、成本 | 原始文件正文 |
| **R2**（私有桶） | 上传的文件、网页快照正文、标准化历史数据 | 索引和关系 |
| **LangSmith** | 每次模型调用、工具调用、子代理任务的原始轨迹 | 业务判定结果 |

**只在 LangSmith 里有的东西**：模型的原始输出原文。被校验器丢弃的字段、被拒绝的抓取网址，都只在那里能看见。查某次运行的完整轨迹，按 metadata 里的 `sourcing_run_id` 过滤。

**刻意不存的**：搜索结果摘要不落库，也不进证据；被拒绝的抓取网址不落库。

## 七、怎么验收

```bash
# 本地
uv run --python 3.11 python -m pytest -q        # 单元与契约测试
uv run --python 3.11 ruff check .                # 静态检查
npx tsc --noEmit                               # Worker 类型检查

# 云端（需要本地 .demo_access_token 和 .env 里的 LangSmith key）
uv run --python 3.11 python scripts/verify_m1_cloud_api.py
uv run --python 3.11 python scripts/verify_m2_cloud_api.py
```

**云端验收的判据**：每个阶段最多跑三次，记录通过率；三次里至少一次全阶段通过即 PASS。**阶段内部的检查不放宽**：精确型号、引文在快照里、快照哈希一致、候选停在长名单、trace 可读回——任何一条不满足就是失败。

原因是：一次寻源是活的网络任务，会因为搜索服务超时、模型限流、某个研究任务没交结果而提前结束。判据要问的是「这套系统能不能产出带来源的候选」，不是「这一次网络和模型有没有同时配合好」。**失败永远是可见的**，有原因码、有 trace。

## 八、已知限制

1. **单轮寻源的完成率不是 100%。** 2026-10-28 全天 20 轮里 12 轮完成，其余各带明确原因。提示词修正后随后 3 轮全部完成。剩余波动来自上游服务与模型输出形状，不是数据一致性问题。
2. **需求的条数与金额由模型给出**，代码不保证（见第四节第 1 条）。
3. **只有一个真实输入样本的抽取稳定性被验证过**（官方 PPTX 两种 + 验收用的小 PPTX）。
4. **运行时日志未接入。** 该账号没有配置 Workers Logs 的 dataset，容器异常只能靠返回体里的错误类型与脱敏消息判断。
5. **研究说的是传感器像素时，需求问的常常是视频输出像素。** 两者不是同一个量，系统会拒绝比较并说明原因，而不是放过。
6. **SIGTERM 中断后的可靠恢复尚未完成**，登记为 M5 必须完成的验收项。容器存活时间变长不等于这个问题解决了。
